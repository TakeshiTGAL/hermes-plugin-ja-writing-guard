# 設計メモ：プッシュ通知の送信キュー

## 背景と目的

現在、プッシュ通知は API サーバーから直接 FCM / APNs に送信している。予約リマインダーのように一度に数万件を送るケースで、以下の問題が出ている。

- 送信処理が API のリクエスト処理と同じプロセスで動くため、一斉送信中に API が遅くなる
- 外部サービスが一時的にエラーを返した場合、再送の仕組みがなく通知が失われる

これを解決するため、通知の送信をキュー経由の非同期処理に切り替える。

## 全体の流れ

1. API サーバーは、通知の内容と宛先を `notifications` テーブルに保存し、ジョブをキューに積む
2. 通知ワーカーがキューからジョブを取り出し、FCM / APNs に送信する
3. 送信結果（成功・失敗・無効なトークン）を `notifications` テーブルに記録する

## キューの選定

| 候補 | 良い点 | 気になる点 |
|---|---|---|
| Amazon SQS | マネージドで運用が楽。既存のインフラに合う | 優先度の制御は、キューを分けて行う必要がある |
| Redis（BullMQ） | 優先度や遅延実行が使いやすい | Redis の永続化と運用の手間が増える |
| PostgreSQL（SKIP LOCKED） | 新しい部品が増えない | 数万件の一斉送信ではテーブルの負荷が心配 |

運用の負担と既存構成との相性を重視し、**SQS を採用する**。

## 優先度

通知を2種類に分け、それぞれ別のキューを使う。

- `notify-high`：パスワード変更、決済完了など、すぐに届けるべき通知
- `notify-bulk`：リマインダー、キャンペーンなど、多少遅れても問題ない通知

ワーカーは `notify-high` を優先してポーリングする。

## 再送と失敗時の扱い

- 一時的なエラー（5xx、タイムアウト）は、指数バックオフで最大5回まで再送する
- 5回失敗したジョブはデッドレターキューに移し、アラートを出す
- 「無効なトークン」が返ってきた場合は再送せず、該当トークンを無効化する

## 重複送信の防止

SQS は同じメッセージが2回以上届くことがある。ワーカーは送信前に `notifications.status` を確認し、すでに `sent` になっていればスキップする。
