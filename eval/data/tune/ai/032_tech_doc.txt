## 概要

検索 API（`GET /api/v2/articles/search`）のページネーションを、オフセット方式からカーソル方式に変更します。

## 背景

現在の検索 API は `page` と `per_page` によるオフセット方式を採用しています。この方式には以下の問題がありました。

- ページが深くなるほどクエリが遅くなる（100ページ目以降で 1.5 秒以上）
- ページ送りの途中で記事が追加・削除されると、同じ記事が重複したり、抜けたりする

## 変更内容

- レスポンスに `next_cursor` を追加しました。次のページを取得する際は、この値を `cursor` パラメータとして渡します
- カーソルは `(published_at, id)` の組み合わせをエンコードした文字列です
- 並び順を保証するため、`(published_at DESC, id DESC)` の複合インデックスを追加しました
- 最後のページでは `next_cursor` が `null` になります

### リクエスト例

```
GET /api/v2/articles/search?q=camping&limit=20
GET /api/v2/articles/search?q=camping&limit=20&cursor=eyJwIjoiMjAyNi0wOS0zMFQxMDowMDowMFoiLCJpIjo4ODIxfQ
```

## 後方互換性

- `page` パラメータは当面使えるように残しています。ただし、レスポンスヘッダーに `Deprecation: true` を付けています
- `page` パラメータは 2027年3月末に廃止する予定です。廃止の告知は別途行います

## パフォーマンス

ステージング環境で、記事数 約120万件のデータを使って計測しました。

| | 変更前（オフセット） | 変更後（カーソル） |
|---|---|---|
| 1ページ目 | 45ms | 38ms |
| 50ページ目 | 620ms | 41ms |
| 200ページ目 | 2,340ms | 43ms |

## テスト

- カーソルの生成・解析のユニットテストを追加
- ページ送りの途中で記事を追加・削除しても、重複や抜けが起きないことを確認する統合テストを追加
- 不正なカーソルを渡した場合に 400 を返すことを確認

## レビューで見てほしいところ

- カーソルのエンコード形式（Base64 の JSON）で問題ないか。将来、並び順の種類を増やすことを考えると、バージョン番号を含めておいたほうがよいかもしれません
- インデックスの追加は、本番では `CONCURRENTLY` で実行する想定です
