# ADR-014: フロントエンドの状態管理に Zustand を採用する

- ステータス：承認済み
- 日付：2026-09-30
- 決定者：フロントエンドチーム

## コンテキスト

管理画面（React + TypeScript）では、これまで状態管理に Redux Toolkit を使ってきた。画面数が増えるにつれ、以下の課題が目立つようになった。

- 小さな状態を追加するだけでも、slice・action・selector の定義が必要で、記述量が多い
- 新しく参加したメンバーが Redux の概念を理解するまでに時間がかかる
- サーバーから取得したデータのキャッシュを Redux で管理しており、再取得や無効化の処理が複雑になっている

## 検討した選択肢

### 1. Redux Toolkit を使い続ける
- 良い点：既存のコードをそのまま使える。実績が多い
- 悪い点：上記の課題が解消されない

### 2. Zustand
- 良い点：記述が少なく、学習コストが低い。React の外からも状態を参照できる
- 悪い点：決まった書き方が少ないため、チーム内でルールを決める必要がある

### 3. Jotai
- 良い点：状態を小さな単位（atom）に分けられ、再レンダリングを細かく制御できる
- 悪い点：状態が多くの atom に分散すると、全体像を追いにくい

## 決定

**クライアント側の状態管理には Zustand を採用する。** あわせて、サーバーから取得するデータの管理は TanStack Query に任せる。

状態管理の課題の多くは、サーバーのデータとクライアントの状態を同じ仕組みで扱っていたことにある。サーバーのデータを TanStack Query に移すと、残るクライアントの状態（モーダルの開閉、フィルター条件、フォームの一時的な値など）は少なくなるため、シンプルな Zustand で十分だと判断した。

## 影響

- 新しい画面は、Zustand と TanStack Query で実装する
- 既存の Redux のコードは、画面を改修するタイミングで順次置き換える。一括での移行は行わない
- ストアの分け方や命名のルールを `docs/frontend/state.md` にまとめる

## 再検討の条件

- クライアント側の状態が大きく複雑になり、Zustand のストアが肥大化した場合
- 移行が1年経っても半分以上残っている場合
