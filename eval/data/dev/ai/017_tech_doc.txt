## 概要

画像アップロード時のリサイズ処理を、API サーバー内の同期処理からバックグラウンドワーカーでの非同期処理に移行しました。

## 背景

現在、ユーザーが画像をアップロードすると、API サーバーがリクエストの中でサムネイル（3サイズ）を生成しています。高解像度の画像では処理に 3〜5 秒かかることがあり、以下の問題が起きていました。

- アップロード API のレスポンスが遅く、p95 が 4.2 秒
- 画像の多い時間帯に API サーバーの CPU 使用率が上がり、ほかのエンドポイントにも影響が出る

## 変更内容

- アップロード API は、元画像をストレージに保存したあと、リサイズのジョブをキューに登録してすぐにレスポンスを返すようにしました
- 新たに `image-resize-worker` を追加し、キューからジョブを取り出してサムネイルを生成します
- 画像レコードに `status` カラム（`processing` / `ready` / `failed`）を追加しました
- フロントエンドでは、`status` が `processing` の間はプレースホルダー画像を表示します
- リサイズに3回失敗した場合は `failed` にし、Sentry に通知します

## マイグレーション

`images` テーブルに `status` カラムを追加します。既存のレコードはすべて `ready` で埋めます。

```
bin/migrate 20261001_add_status_to_images
```

## 確認方法

1. ローカルで `docker compose up worker` を実行してワーカーを起動
2. 管理画面から 10MB 程度の画像をアップロード
3. アップロード直後にプレースホルダーが表示され、数秒後にサムネイルに切り替わることを確認
4. ワーカーを止めた状態でアップロードし、`status` が `processing` のまま残ることを確認

## 影響・注意点

- デプロイ時は、ワーカーを先にデプロイしてから API をデプロイしてください
- 外部連携の API で、アップロード直後にサムネイル URL を参照しているクライアントがある場合は、`status` を確認するように案内が必要です
